# DECISIONS — stocktest 交易記帳

每個「選 A 不選 B」的判斷追加一條。最新在最上面。

## 2026-09-29 · 庫存已實現：改計算口徑，而非只改文案

- **選**：庫存損益頁的「已實現損益」KPI 改用 `get_realized_pnl_by_stock()`（全部股票、含已賣光）。
- **不選**：只在 caption 註明「僅計仍有庫存的股票」。
- **為什麼**：同事期望兩頁的已實現能對起來；只改文案，數字仍偏低、仍會被質疑。改口徑後同區間兩頁一致，且順手修掉「報酬率分子（僅持倉）／分母（全部）不一致」的隱性 bug。

## 2026-09-29 · aggregate_by 除零：用 float("nan")，不用 pd.NA、不引入 numpy

- **選**：`買進成本.replace(0, float("nan"))`。
- **不選**：維持 `pd.NA`（會轉 object dtype 讓 `.round()` 崩潰）；或引入 numpy 用 `np.where`。
- **為什麼**：`float("nan")` 保持整欄 float dtype，`.round(2)` 正常、無成本的股票顯示 NaN；一行改動、不新增相依、風險最低。

## 2026-09-29 · 交易輸入清空：加按鈕，不強改自動重置流程

- **選**：新增「🧹 清空輸入列」按鈕（複用既有 `te_rreset` 重置機制）。
- **不選**：直接改寫送出後的自動重置時序（尚未定位到為何未觸發，貿然改動可能引入賣出逐筆流程的回歸）。
- **為什麼**：先給同事一個確定有效的止痛工具；根因待可穩定重現後再處理，避免動到剛改過的多筆賣出逐筆配對邏輯。

## 2026-09-30 — 底價依升降單位「向上」進位，且不套當沖減半稅
- 選：取「可掛單、且賣了保證不虧」的最低價，並以一般證交稅 0.3%（ETF 0.1%）計算。
- 不選：顯示未進位的理論值（如 946.37），同事無法直接掛單；也不套當沖減半，因為庫存賣出多數不是當沖，用保守值才不會誤賣虧損。

## 2026-10-01 · 持倉成本統一用「自定沖銷＋其餘先進先出」
- 選：`compute_position_and_cost_by_stock` 預設 `CUSTOM_PLUS_FIFO`，與庫存損益頁同口徑。
- 不選：維持 `CUSTOM`（只看自定沖銷）——未設規則的賣出不扣成本，均價失真，且兩頁數字對不上。
- 為什麼：所有賣出都必須沖掉某些買進，持倉成本才正確；FIFO 是規則未涵蓋時最常見、券商也採用的預設。

## 2026-10-01 · 失效沖銷規則：只警示，不自動刪除
- 選：在自定沖銷設定頁列出失效規則，由使用者到「已配對一覽」手動刪除重設。
- 不選：程式自動清除或自動改指新 id——刪的是正式資料（同步試算表），且無法確定原本要配哪一筆買進。
- 為什麼：計算上失效規則已被略過、由 FIFO 補配，數字不會錯；清理交給知道原意的人做。

## 2026-10-01 · 底價維持「含賣出手續費＋證交稅」，加強說明而非改公式
- 選：保留打平價定義，在表格說明與表頭提示寫清楚「不是均價進位」並附實例。
- 不選：改成均價進位（如國巨 870）——實際賣在該價扣費稅後會虧 1.2 萬，會誤導下單。

## 2026-10-01 · 損益顏色維持台股慣例「紅賺綠賠」
- 選：全站維持紅＝賺、綠＝賠，並在庫存損益頁註明。
- 不選：改會計慣例「負數紅色」——與券商 App、本 app 現價漲跌（紅漲綠跌）相反，且只改一張表會與 KPI 卡片互相矛盾。

## 2026-10-01 · 套件上限對齊本機測試版本，而非 Cloud 當下裝到的最新版
- 選：上限設在本機實測過的版本（pandas<3、streamlit<1.52、anthropic<1…）。
- 不選：不鎖上限、讓 Cloud 每次重裝都拉最新版（本次就裝到 pandas 3 / streamlit 1.64 / Python 3.13，跟本機測試環境不一樣）。
- 為什麼：測試綠燈只代表本機版本沒問題；Cloud 環境要跟本機一致，才能算是驗證過。

## 2026-10-01 · 寫回去重用「內容指紋」，不用 ORM 變更追蹤
- 選：寫回前把五張表內容算 sha256，跟上次寫回（或剛載入）時的指紋相同就略過。
- 不選：用 SQLAlchemy flush 事件追蹤哪些表被改——`query(...).delete()` 這類批次刪除（交易輸入、匯入頁大量使用）不會經過 flush，會漏掉真正的變更。
- 為什麼：比對內容不管用什麼方式改都抓得到，不會漏寫；多花的只是一次本機 SQLite 查詢，比整表寫回試算表便宜很多。

## 2026-10-02 · 重置輸入列：換新的 widget key，不靠刪 session_state
- 選：送出／清空後，新的空白列用沒用過的列號（`te_rowseq` 遞增）當 key。
- 不選：只 `del st.session_state[key]` 後沿用同一個 key（瀏覽器端同名 widget 會保留舊值並再送回伺服器，實測重現）；或改成指定 `st.session_state[key] = None`（不同 Streamlit 版本行為不一，且 widget 建立後不能再改）。
- 為什麼：新 key 一定會在瀏覽器畫出全新元件，不受 Streamlit 版本與前端快取影響。

## 2026-10-02 · 交易輸入列隱藏 −/＋ 按鈕，而不是把欄位撐更寬
- 選：只在輸入列容器（`st-key-te_inrows_*`）用 CSS 隱藏 −/＋，保留 ✕。
- 不選：只靠加寬欄位——一般筆電寬度（1280px）下，三個按鈕仍佔掉大半，數字還是被截斷。
- 為什麼：同事都是直接打數字，股數一跳 100、價格一跳 0.01 的按鈕幾乎用不到；用容器 key 限定範圍，不影響沖銷面板與設定頁的數字框。

## 2026-10-02 · 送出變慢：減少寫回試算表的連線次數，不改成背景同步
- 選：同步仍在送出當下完成（畫面等它寫完、驗證完才顯示成功），只把一次寫回的連線從約 17 次減到約 7 次：重用試算表連線、一次抓全部分頁、防呆／回讀只讀 id 欄、滾動備份每 10 分鐘最多一份（`SHEET_BACKUP_MIN_INTERVAL` 可調）。
- 不選：改成背景執行緒同步、畫面先回應——同事看到「已新增」時資料其實還沒進試算表，失敗也看不到提示；這個 app 過去的掉單都出在同步，寧可多等 2～3 秒。
- 為什麼滾動備份可以降頻：最新狀態每次都會寫進固定備份分頁 `trades_backup`；滾動備份是為了回溯歷史，每筆都備份反而會在連續送出幾分鐘內把 10 份額度用完，擠掉較早的歷史，降頻後能回溯的時間反而更長。

## 2026-10-02 · 寫回加鎖排隊，並且讀不到 id 時就不寫（不再跳過防呆）
- 選：`sync_db_to_sheet` 用一把鎖讓寫回排隊，鎖內才讀 DB；寫回前讀不到試算表 id、寫入後回讀不一致，都回報失敗、不記成已同步。
- 不選：維持原狀（兩人同時送出時兩個寫回會交錯：較舊的快照最後寫入並修剪掉新列，交易從試算表消失；讀 id 失敗時原本會直接略過防呆照寫）。
- 為什麼：這兩個都是「可能默默弄丟資料」的漏洞，修掉不影響速度。回讀也從「筆數夠就好」改成「id 完全一致」。

## 2026-10-02 · 正式資料改放 Neon Postgres，試算表降為備份
- 選：Neon 免費版 Postgres（閒置自動休眠、有連線自動醒來），試算表改成每日匯出的唯讀備份。
- 不選：繼續優化試算表（再快只能到 1～2 秒，且要改成「只追加」寫法，刪改時找錯列的風險更高）；Supabase 免費版（7 天無活動要人工到後台恢復）；改寫成網站（不解決根因、工作量大）。
- 為什麼：慢和掉單都來自「記憶體一份、試算表一份」的雙份資料設計；換成單一資料庫兩個問題一起消失，且程式本來就支援 DATABASE_URL，頁面不用改。

## 2026-10-02 · 有 DATABASE_URL 就以資料庫為準，自動停用試算表模式
- 選：`USE_GOOGLE_SHEET` 只在沒有 `DATABASE_URL` 時生效；切換只需在 Secrets 加一行，回退刪一行。
- 不選：要求同時把 `USE_GOOGLE_SHEET` 改成 false——漏改一個就會變成兩邊都當正式資料、互相覆蓋。

## 2026-10-02 · Postgres 建表比照 SQLite 的寬鬆行為（不建外鍵、文字不限長度）
- 選：Postgres 上不建外鍵限制、String(n) 一律不限長度。
- 不選：照模型定義建外鍵與長度——正式資料有 26 條失效沖銷規則（指向已刪交易）會讓搬家失敗；主檔有 24 字的類股指數代號會讓主檔寫入失敗。
- 為什麼：這次的目標是「換儲存位置、行為不變」；資料品質（清理失效規則）另案處理。

## 2026-10-02 · 讀取交易與沖銷規則固定排序
- 選：交易依 id、沖銷規則依（賣出 id, 買進 id）讀取，兩種資料庫都一樣。
- 不選：沿用不指定順序（SQLite 剛好是插入順序；Postgres 不保證）。
- 為什麼：正式資料有 5 個買進批被超額配對，此時規則套用順序會影響損益；固定排序後試算表與 Postgres 算出的數字逐位元一致（已驗證，且與原本插入順序結果相同）。

## 2026-10-02 · 本機的 Neon 連線字串叫 NEON_DATABASE_URL，不叫 DATABASE_URL
- 選：`.env` 用 `NEON_DATABASE_URL`，只給搬家／匯出腳本用。
- 不選：`.env` 直接放 `DATABASE_URL`——本機開 app 或跑頁面測試就會直接改到正式資料庫（同 .env 試算表模式寫到正式表的教訓）。

## 2026-10-02 · 每日備份用 GitHub Actions，不放在 app 裡
- 選：GitHub Actions 每天台灣 22:00 執行 `scripts/export_db_to_sheet.py`，失敗時 GitHub 寄信。
- 不選：app 內「每天第一次存檔時順便匯出」——會讓某一次送出變慢，且沒人用 app 的日子就不會備份。

## 2026-10-02 · 交易輸入區用 st.fragment，而不是 st.form
- 選：把輸入列、加列／清空、賣出沖銷配對、送出確認包成 fragment；區內操作只重跑這一區，送出成功才整頁重跑。
- 不選：`st.form`——表單內不能放「多輸入一筆」「沖銷快捷鍵」等一般按鈕，手續費即時估算也要等送出才看得到，操作流程要大改。
- 為什麼：整頁重跑要重畫全部持股、KPI、交易明細，正式站每格輸入完都頓好幾秒，太快接著打的數字還會被重畫蓋掉（同事回報「點空白處數字就消失」）。本機量測離開欄位到畫面更新：2.0 秒 → 0.35 秒。

## 2026-10-02 · 大量刪除前強制備份；正式資料上不顯示開發用按鈕
- 選：清空全部要手打「確認清空」、區間刪除改兩段式（先顯示筆數再確認）、刪除整檔股票維持勾選確認；三者刪除前都先把資料庫匯出到試算表，**備份失敗就不刪**。「產生模擬數據」與側欄「清空所有庫存資料」只在本機開發資料庫出現。
- 不選：只加「你確定嗎？」按鈕——同事共用管理者帳號，連按兩下很容易；也不選完全移除清空功能（重新匯入券商資料時仍需要）。
- 為什麼：換成資料庫後已沒有「試算表縮水就中止寫回」那道保險，一鍵刪除會直接生效；先備份才有東西可以救。

## 2026-10-05 · 股票輸入（仿 Yahoo）的分頁＝存起來的篩選條件，每個買賣人各自一組
- 選：分頁只存條件（日期範圍、股票清單），交易仍只有一本總帳；同一筆交易可出現在多個分頁；新頁另開，舊「交易輸入」頁保留。（Jonathan 選定）
- 不選：Yahoo 原生的「每個分頁是獨立帳本」——要幫現有 544 筆交易分派分頁、改沖銷引擎與所有報表，風險高；也不直接改舊頁，避免同事正在用的流程被打斷。
- 為什麼：改動最小、不用搬資料，分頁數字與其他頁同一套引擎；有起始日的分頁若賣出找不到分頁內的買進，畫面明確提示而不是悄悄算錯。

## 2026-10-05 · ~~新頁的賣出不自動建立沖銷規則（走先進先出）~~（同日已改，見下一條）
- 選：新頁輸入的賣出只寫交易，損益由「自定沖銷＋其餘先進先出」計算。
- 不選：比照舊頁自動建立「接近均價」沖銷規則——新頁主打快速、防呆輸入；需要指定沖銷批次時用舊頁或自定沖銷設定頁。

## 2026-10-05 · 新頁賣出改為有沖銷配對（推翻上一條）
- 選：新頁賣出也顯示沖銷配對，口徑與舊頁相同（預設接近均價、可換方式、可逐批改，合計須等於賣出股數），送出時寫入自定沖銷規則。
- 不選：只走先進先出——Jonathan 試用後要求同事能指定沖哪幾批，且兩頁口徑一致才不會同一筆賣出在不同頁算出不同損益。

## 2026-10-07 — 仿Yahoo 交易明細修改：用「✏️ 展開小表單」而不是整張 data_editor
- 選 A：每筆一個 ✏️，展開日期／股數／股價小表單，逐筆儲存、逐筆防呆（漲跌停、持股不足、沖銷配對清除提醒）。
- 不選 B：整張表改 data_editor（舊交易輸入頁做法）——批次儲存難逐筆防呆，也和這頁乾淨的 Yahoo 風格不搭。
- 股數改了就清自定沖銷（不嘗試自動縮減配對）：與舊頁口徑一致、最不會算錯；要指定配對到「自定沖銷設定」。

## 2026-10-07 — 仿Yahoo 分頁口徑：以買進歸屬（不選「只用分頁內交易自己配對」）
- 選 A：沖銷用買賣人全部交易照全站引擎配對，分頁只取買進符合條件的批次（持股、已實現都跟著批次走）。
- 不選 B（原做法）：只餵分頁內交易給引擎——起始日前的庫存在分頁內被當成「找不到買進」，Peggy 覺得很怪；而且同一筆賣出在不同分頁會配到不同批次，跟庫存損益頁對不起來。
- 結果：「全部」分頁＝庫存損益頁；有日期的分頁＝「這段期間買進的那幾批現在怎樣了」。

## 2026-10-07 — 仿Yahoo 多筆輸入只開放買入
- 選 A：買入可多列一次送出；賣出一次一筆。
- 不選 B：賣出也多列——每筆賣出都要配沖銷，多筆同時配會互相搶同一批庫存，畫面與防呆都會變很複雜；Peggy 的需求也只提買入。

## 2026-10-07 — 仿Yahoo 分頁改成「投資組合」並屬於登入帳號
- 選 A（使用者選）：人＝分頁、拿掉買賣人下拉；分頁加 `owner`（登入帳號），每個帳號只看到自己加過的分頁。
- 不選 B：保留下拉、分頁裡再多一種「別人的全部帳」——切人有兩種方式，容易搞混。
- 不選 C：列出所有有權限買賣人的分頁（免改表）——admin 會被所有買賣人塞滿。
- 「全部帳」不另設類型欄，而是「沒設日期、沒限定股票」的分頁即是；少一個欄位、少一種狀態要同步。

## 2026-10-08 — 仿Yahoo 搜尋股票：選了就「只顯示那一檔＋自動展開」
- 選 A：搜尋後持股表只留那一檔並展開，清除搜尋回全部。
- 不選 B：保留全部列、自動捲動到那一列——Streamlit 沒有原生捲動，要靠注入 JS 操作父頁面，部署環境換版就可能失效；而且展開區很長時捲動位置會跳。
- 搜尋框用可打字篩選的 selectbox 而不是 text_input：不用按 Enter、打「國」或「2327」都會即時列出候選，不會打錯字找不到。
